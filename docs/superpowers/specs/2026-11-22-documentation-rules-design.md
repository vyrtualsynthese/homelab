# Documentation rules, and the two sections that need one — design

Date: 2026-11-22
Status: draft for operator approval
Supersedes: nothing. Extends
[2026-11-17-docs-for-the-operator-design.md](2026-11-17-docs-for-the-operator-design.md), which built
the three reading sections this page constrains.

## 1. Intent

One reader: the operator. Two usages, and a third that is really the second kept honest.

1. **Remember how and why the place works**, in prose that can be read end to end, not a table of
   facts. `how-it-works/` and `running-it/` do this today and stay the model for it.
2. **Look up a fact that must be current** — which hostname is public, which claim is backed up,
   which Secret a chart expects. This layer cannot be kept right by hand, and must not be trusted
   when it is stale.
3. **Face a loss or an intrusion** and have a page that says what to do, in the order to do it,
   including the case where nothing survives. Backups and security are the two subjects where a
   missing page is the failure, and today both are scattered across four and five pages in three
   different tabs.

The change wanted: written rules that say which kind of page answers which question, where each
fact lives, and who may edit it — plus two real sections built on those rules, and the technical
facts the rules describe generated from the repository rather than typed.

The failure this fixes is drift, not bad prose. `reference/routes.md` lists 44 route files' worth of
hostnames by hand. `applications.md` is a hand-kept catalogue of ~50 applications. `status.md` is a
snapshot dated 2026-11-14 whose own header disagrees with itself about which day it describes. Each
one is a page whose correctness decays without any edit, and nothing notices when it does. Only the
last of the three is beyond repair, and it is retired rather than migrated.

## 2. What exists today

Measured on `develop` at `6fbdf255`, 2026-11-22.

- Seven nav tabs: Start here, How it works, Running it, Reference, Runbooks, History, Agent work.
  The living pages are about 65,000 words; `docs/superpowers/` is untouched by this project.
- Of the 73 living pages, none carries the full blockquote this design asks for, 53 carry a partial
  one, the `Kind:` label in use takes seven different values (`living page`, `snapshot`,
  `completed record`, `living procedure`, …), and two pages have a `Sources` line. The four kinds are
  therefore a rule for pages written from now on, not a tree-wide rewrite.
- `docs/runbooks/` holds 19 files and is a shelf rather than a section: restore, the internal CA,
  authentik wiring and K3s upgrades sit side by side with nothing in common but having been run
  once. `runbooks/README.md` already carries the one thing worth keeping — a status per procedure
  (`proved <date>`, `pending`, `completed record`).
- Backup material is in four places: `how-it-works/backups.md` (mechanism), `running-it/disaster-recovery.md`
  (what a loss costs), `runbooks/restore.md` (the procedure and the drill log),
  `runbooks/last-resort.md` (no cluster at all), plus `runbooks/postgres-restore.md`.
- Security material is in five: `secrets.md`, `how-it-works/identity.md`, `how-it-works/network.md`,
  the `lan-only` list in `AGENTS.md` §4, and `decisions/2026-11-21-sovereign-eu-providers-only.md`.
- **56 references point into `docs/runbooks/` from outside `docs/`** — chart `values.yaml` comments,
  `cluster/helm/backup/README.md`, `prometheus/values.yaml` and the restore-drill ConfigMap,
  `hack/internal-cert.sh`, `hack/vikunja-seed.sh`, `.github/renovate.json`, `AGENTS.md`. These files
  are pinned paths, not preferences.
- `hack/check_docs_links.py` already fails a PR on a broken relative link, and
  `hack/check-app-version.sh` is the existing pattern for "a fact must match its source or the check
  fails".
- The site is `docs.kub.local`, built per repository and ref by `cluster/helm/docs-site`, behind
  `lan-only` and the authentik gate. A repository's own `mkdocs.yml` is honoured verbatim, so the nav
  is the site's nav.

## 3. Goals

- Four page kinds, each with a shape and an owner, and every page declares which it is.
- Rules that are mostly mechanical, so a busy month cannot quietly break them: a check that fails,
  or a review step that has an artifact.
- Backup and security as sections you enter with an incident, not a subject index.
- Every fact that can be derived from the repository, and that a dependency bump cannot change, is
  generated, carries a banner saying so, and is regenerated by a check.
- The hardening pass can see which pages drifted, and files cards for them — without editing.

## 4. Non-goals

- Teaching anybody. The public-facing material is a separate project with its own readers, tone and
  exposure model; nothing here is written for it, and nothing here becomes public.
- Rewriting the argument in `how-it-works/`. Those pages are the model the new sections imitate.
- Moving pages that something outside `docs/` cites, unless the citing file moves in the same change.
- Editing `docs/superpowers/`, and editing the `hardening-pass` skill from this repository: it lives
  in the operator's config repository, and a session writes in its own project.
- Re-bannering all 73 existing pages in one change. A page adopts its true kind and its `Sources` the
  next time it is edited; the checks enforce it there.
- Making the docs site public, or adding a second site.

## 5. Anti-goals

- **A second store of the same fact.** A generated page and a hand-written page stating the same
  count is the defect this design exists to prevent.
- **A rules page nobody applies.** Every rule is either checked by a script or named in a review
  step with the artifact it produces.
- **A nav that mirrors the file tree.** The reading order and the storage layout answer different
  questions; the tree follows the code, the nav follows the reader.
- **Prose that reads like a changelog.** A human page states what is true now; the route to it is a
  decision record or a plan, linked, not pasted in.

## 6. Constraints

- MkDocs Material 9.8.2 in the builder; the body must also render on GitHub, so blockquotes and
  never `!!!` admonitions.
- The builder publishes `main` and `develop` only. A page is invisible on the site until it merges.
- Agents read the GitHub render, not the site: the site is behind authentik and an agent cannot get
  through the gate. Anything an agent must read has to be a file in git.
- Checks must run with no cluster, like the rest of `hack/`.
- `cluster/argocd/**` keeps CRLF; Markdown is LF. Chart READMEs and values files updated by this
  work keep their existing endings.
- Plain language: a media or design term is glossed once, in plain words, the first time it appears
  in a page.

## 7. Approaches considered

**A — Two incident-shaped sections, runbooks redistributed. (chosen)** New `docs/backup/` and
`docs/security/`, cut by what you face rather than by subject; the existing runbooks move into the
nav position where they are used, keeping their paths where the repo cites them. A rules page and a
check script make the conventions mechanical.

**B — Landing pages only.** Two index pages that sequence the existing files, moving nothing.
Cheapest, zero link risk, and it fixes nothing: the home page already does this, and the four backup
pages stay four pages.

**C — Split the tree into a handbook and a generated fact layer.** `docs/handbook/` and `docs/facts/`
as the top level. Cleanest by construction, and the largest diff in the repository's history; the
benefit only arrives when every page and every citing file has moved.

A delivers the sections, keeps the 56 pinned paths intact by treating the nav as the section and the
path as the storage, and can land in four reviewed stages. The operator chose A on 2026-11-22.

## 8. The design

### 8.1 Four kinds of page, and who may edit each

| Kind | Answers | Written by | Edit rule |
|---|---|---|---|
| Explanation | why the place is shaped this way | an agent, for the operator | rewritten when the shape changes, re-dated |
| How-to | what to do, in order | an agent, then the operator after it has been run | the body follows reality; a change to reality changes it in the same PR |
| Reference | a table of current fact | a script, from the repository | never hand-edited; regenerate and commit |
| Record | what was true, or what was decided, on a date | the session that did it | never edited; a correction is a new record |

A page declares its kind in its opening blockquote. The kind decides who may touch it, which is the
part that stops an agent improving a snapshot.

**Migration is prospective.** The banner check applies to the pages a pull request changes, and
prints a tree-wide report for the rest. The existing labels map onto the four kinds — `living page`
is an explanation or a how-to depending on its tab, `living procedure` and `living runbook` are
how-tos, `snapshot` and `completed record` are records — and a page adopts its true kind the next
time it is edited. Stamping `Verified` on 73 pages nobody re-read would make the freshness report
lie on its first run, which is the one thing this design must not do. R7's length limits and R12's
runbook statuses are prospective for the same reason; R12 is already satisfied by
`runbooks/README.md`, which carries a status for all 19.

### 8.2 Navigation, and where every page lands

Eight tabs. `Runbooks` dissolves as a tab — its pages are listed where they are used, at their
existing paths. The nav is the reading order; a file keeps its path when something outside `docs/`
cites it.

| Tab | Pages | Note |
|---|---|---|
| Start here | `README.md`, `documentation-rules.md` | the rules are a page, so they can be read |
| How it works | the ten existing topic pages, minus Backups | unchanged otherwise, Applications included |
| Running it | the day-2 pages, and the operational procedures: `traefik-release`, `k3s-upgrade`, `renovate`, `gpu-operator`, `argocd`, `cloud-monitoring`, `alert-relay`, `postgres-add-database`, `vikunja-board-seed` | `runbooks/README.md` becomes its procedure index, rewritten as a status table |
| Backups | §8.3 | new |
| Security | §8.4 | new |
| Reference | routes, the chart contract (`charts/README.md`), charts, metrics, logs, alerts, dashboards, SSO matrix, observability conventions | `secrets.md` moves to Security; two agent-facing pages join the nav instead of getting an exemption |
| History | decisions, audits, completed records: `books-cutover`, `docs-site-first-run`, `vikunja-database`, `vikunja-first-start` | records, never edited |
| Agent work | `agent-work.md`, `agent-protocol.md` | unchanged |

`status.md` is retired rather than migrated. It cannot be generated, because it reads the cluster; a
record may not be edited, and its own standing instruction was to refresh it, which is why its two
dates already disagree. Its job is covered without it: `applications.md` says what exists, ArgoCD and
Grafana say what is broken now, `running-it/every-day.md` says where to look, and the two open faults
keep their own pages. The retirement is one file, its inbound links, and the "only page that carries
counts" sentence in `docs/README.md`.

Moves, each with its citing files updated in the same change:
`running-it/disaster-recovery.md` → `backup/what-a-loss-costs.md`. Everything else stays at its path:
`secrets.md` is listed under Security, `how-it-works/applications.md` stays where it is and stays
hand-written (§8.6), and `how-it-works/backups.md` stays because `cluster/helm/backup/README.md` and
`cluster/helm/syncthing/README.md` cite it.

### 8.3 The Backups section

Entered with a loss, not a subject. Every page answers one question, and the procedures keep their
paths.

| Page | Path | Answers |
|---|---|---|
| Backups | `backup/README.md` | what is protected, what is deliberately not, what a loss costs, and the order to read |
| What a loss costs | `backup/what-a-loss-costs.md` | per failure: what is gone, what comes back, from where |
| How the jobs work | `how-it-works/backups.md` | the restic repositories, the bucket, the schedule, the verifier, the alerts |
| Coverage | `backup/coverage.md` | **generated** — one row per backed-up claim: stream, schedule, size, kind |
| A file or a claim | `backup/a-file-or-a-claim.md` | one file was deleted, or a claim was wiped; what to bring back and what not to touch |
| A database is corrupt | `backup/a-database.md` | the staged SQLite copy, `integrity_check`, and the swap |
| PostgreSQL | `backup/postgresql.md` | `globals.sql` first, then the dump; the role and the database |
| A node's disk died | `backup/a-node.md` | what the node took with it, the rebuild order, which claims are stranded |
| No cluster | `backup/no-cluster.md` | `runbooks/last-resort.md` as it is, listed here |
| Everything | `backup/everything.md` | the house is gone: hardware, domains, the OVH account, Bitwarden, the CA root, GitHub, then rebuild |
| Restore a backup | `runbooks/restore.md` | the procedure with a cluster, and the drill log |
| Restore PostgreSQL | `runbooks/postgres-restore.md` | the standalone database restore |

Two facts the section must state plainly, because they are the honest ones: the bulk media is one
copy by decision and a fire ends it; and "the data comes back and is readable" is proved, while
"a cluster comes back" is not.

`backup/everything.md` is the page that does not exist anywhere today. It starts outside the
cluster: what you must be able to produce with no machine of yours working — the domain registrar,
DNS, the OVH tenant, the bucket credentials, the restic password, the Bitwarden recovery code, the
CA root on its USB stick, the GitHub account and its token. Then the dependency order to rebuild.

### 8.4 The Security section

The section states what is enforced and what would hurt, not how traffic works — `network.md` and
`identity.md` keep that argument.

| Page | Path | Answers |
|---|---|---|
| Security | `security/README.md` | the model in one page: nothing public but a named list, one gate, one identity, no secret in git |
| What is enforced | `security/enforcement.md` | one row per guarantee, with the thing that enforces it and the command that proves it: `lan-only`, the forward-auth gate, native OIDC, TLS, Secret handling, the read-only MCP account, pinned images, EU-only providers |
| Critical points | `security/critical-points.md` | the load-bearing things ranked, each with what breaks, where its backup is, and which page recovers it: authentik and its database, the internal CA root, the restic password and the bucket, the `lan-only` middleware, the single Traefik replica, the OVH tenant, the account that owns the repository |
| Secrets | `secrets.md`, its path unchanged | every Secret a chart expects: keys, consumer, origin — never a value |
| Wire an app to authentik | `runbooks/authentik-apps.md` | the procedure, at its cited path |
| The internal CA | `runbooks/internal-ca.md` | minting, signing, the root's two copies |
| The certificate store | `runbooks/acme-store.md` | the ACME store and its weekly limit |
| Public names | `reference/routes.md` | **generated** — the hostname list, which the README filters to the public ones |

`critical-points.md` is the page the operator asked for by implication: "what are the critical
points". It names nine or ten things, each with a failure sentence and a recovery link, ordered by
how much of the homelab goes with it.

### 8.5 The rules page

`docs/documentation-rules.md`, in the nav under Start here. Numbered rules, each marked **Check**
(a script enforces it) or **Review** (a person or agent verifies it, and says what the artifact is).
The rules:

| # | Rule | Enforced by |
|---|---|---|
| R1 | One fact, one home. A second page states it by link, never by copy. | Review |
| R2 | Every page declares one of four kinds, and the kind fixes who may edit it. | Check: banner |
| R3 | The opening blockquote carries In one line / Use it when / Verified / Kind / Sources. | Check: banner |
| R4 | The nav is the reading order. A page cited from outside `docs/` keeps its path; it is listed in nav where the reader needs it. | Check: references |
| R5 | A generated page is never hand-edited. It carries a banner, its sources, and its regenerate command. | Check: regenerate and diff |
| R6 | A change that alters behaviour updates the page that owns it, in the same pull request. | Review |
| R7 | Shape: answer first, then why, then procedure, then links. 300–800 words for an explanation, at most 1,200 for a how-to, one Mermaid diagram where a flow is described. | Review |
| R8 | Plain language, one gloss per domain term, the first time it appears. | Review |
| R9 | No secret value ever, in any page or any example. Keys and locations only. | Check: secret scan |
| R10 | A record and a snapshot are dated and never rewritten. A correction is a new record. | Review |
| R11 | A procedure states preconditions, commands, the output that means success, and the rollback; a destructive step says so first. | Review |
| R12 | A runbook exists only after it has been run; its status is `proved <date>`, `pending` or `completed record <date>`. | Review |
| R13 | Links are relative inside `docs/`; bodies use Markdown that renders on GitHub as well as MkDocs. | Check: links |
| R14 | A new page and its nav entry land in the same commit. A page the nav does not list is a defect. | Check: nav |
| R15 | A page older than the last change to its Sources is stale: the hardening pass files a card, and does not edit the page. | Check: staleness report |
| R16 | A hand-written catalogue names exactly the set its source declares. A missing row and a row for something that no longer exists are both failures. | Check: catalogue |

### 8.6 The generated layer, and the one page that stays written

`hack/gen_docs.py` writes two pages from the repository, with a header naming the sources and the
command. `--check` regenerates into a temporary directory and fails on any difference, the way
`check-app-version.sh` compares a tag to its `appVersion`.

| Page | Source | What it renders |
|---|---|---|
| `reference/routes.md` | every `kind: IngressRoute` under `cluster/helm/` | hostname, application, namespace, middlewares, public or not |
| `backup/coverage.md` | `cluster/helm/backup/values.yaml` | stream, schedule, node, claim, namespace, kind |

`how-it-works/applications.md` stays hand-written, for three reasons that each rule out generation:

- its "What it is" column is the operator's own gloss and has no source in the repository;
- its Node column deliberately means "where the pod last ran", read from the cluster — a check that
  runs with no cluster cannot reproduce it, and a `nodeSelector` column would quietly mean something
  else;
- image tags and chart versions are what Renovate bumps nightly, so a column carrying them turns the
  check red after every merge and stays red until someone unrelated regenerates it.

What replaces generation is a set check: `catalogue` reads the Application names from
`cluster/argocd/projects/` and from the page's own table, and fails on a row without a file or a
file without a row. The columns that drift quietly — node, chart pattern — are what the staleness
report is for. For the same reason nothing generated carries an image tag, a version, or a number a
dependency bump changes: the measured sizes stay in the `values.yaml` comments beside the row that
owns them, and changing one is a deliberate edit that regenerates the page in the same commit.
No generated page carries a timestamp either — a date in the output would make `--check` fail on
every run; the date a page was generated is the date of the commit that touched it.

Generated pages are committed, not built at render time. The builder could generate them, and then
GitHub and every agent would see a page that does not exist; the repository is the reading surface
for agents, and the design keeps one copy.

### 8.7 Freshness, Sources, and the hardening pass

The blockquote gains one line:

```markdown
> **Sources** `cluster/helm/backup/values.yaml`, `cluster/helm/backup/templates/`
```

`Sources` names the files or directories the page describes. `hack/check_docs_staleness.py` prints
every page whose `Verified` date is older than the newest commit touching one of its sources, with
that source and its date. It changes nothing and exits 0, because a stale page is not a broken build.

That list is what the hardening pass reads. The pass stays read-only: it runs the report and files
one card per stale page, naming the page, the source that moved and its date. The refresh is its own
task, on its own branch, where the diff is reviewed like any other.

The step belongs in `docs/agent-protocol.md`, which the skill already instructs a pass to read. A
card in the `config` project asks for the one-line pointer in the skill itself, since that file
lives outside this repository.

### 8.8 The checks

One entry point, `hack/check-docs.sh`, run by hand and by the test suite, modelled on
`check-charts.sh`:

| Check | Fails on | Scope |
|---|---|---|
| generate | a generated page differs from its source | the two generated pages |
| links | a relative Markdown link does not resolve | the whole tree |
| references | a `docs/**.md` path cited anywhere in the repository does not exist | the whole tree, every file type |
| nav | a page under `docs/` outside `superpowers/` has no nav entry, or an entry has no file | the whole tree |
| banner | a changed page does not open with the five-line blockquote | changed pages; a report for the rest |
| catalogue | the application table and `cluster/argocd/projects/` disagree | one page |
| secrets | a value-shaped pattern appears in any page | the whole tree |
| staleness | nothing; it prints dated drift and exits 0 | the whole tree |

`references` is the check R4 needs and does not have today: `check_docs_links.py` walks only `*.md`,
while most citations of these paths live in `values.yaml` comments, `hack/*.sh`, `relay.py` and
`.github/renovate.json` — 37 files. It extracts every `docs/` path from every tracked file and fails
when one does not resolve.

Rule by rule: R2, R3, R4, R5, R9, R13, R14, R15 and R16 are mechanical. The rest are review, and the
rules page says so rather than pretending otherwise.

### 8.9 What changes outside `docs/`

- `mkdocs.yml`: the eight tabs, and the pages each one lists.
- `AGENTS.md` §6: `hack/check-docs.sh` joins the list of checks a change runs, and §4's security
  paragraph points at `security/critical-points.md`. Two paragraphs, no restructure.
- `docs/agent-protocol.md`: the staleness step, and the rule that a documentation refresh is its own
  card.
- The two chart READMEs and `AGENTS.md` that cite a moved page, if any move is chosen that touches a
  pinned path — the plan avoids them.

## 9. Delivery in four stages

Each stage is a pull request rebased on `develop`, reviewed, merged before the next starts.

| Stage | Contains | Usable afterwards |
|---|---|---|
| 1 | `documentation-rules.md`, `hack/gen_docs.py` converting `reference/routes.md`, `hack/check-docs.sh` with the `generate`, `links`, `references`, `nav`, `banner`, `catalogue` and `secrets` checks, the `mkdocs.yml` changes those need, `status.md` retired, `AGENTS.md` §6 | The rules exist, the routes page is true, and a PR can fail on them |
| 2 | `docs/security/` (3 new pages), `secrets.md` re-listed, the three security runbooks in nav, the Security tab | Security can be read as a section |
| 3 | `docs/backup/` (7 new pages plus the two moved), `backup/coverage.md` generated, the restore runbooks in nav, the Backups tab | Backup can be entered from a loss |
| 4 | `check_docs_staleness.py` and its report, the `agent-protocol.md` step, the `Runbooks` tab dissolved, the "Start here" page and both section landings rewritten, `docs/README.md` rewritten | The pass files stale cards; the nav is final |

Stage 1 comes first because it is the only stage whose rules constrain the others; stage 4 last
because the nav's shape depends on both new sections existing. No stage creates an empty tab: a
section's tab is added by the stage that writes its pages.

## 10. Verification, per stage

1. `hack/check-docs.sh` exits 0 (stage 1 onward), and `hack/tests` still passes:
   `uv run --with-requirements hack/tests/requirements.txt python -m pytest -q hack/tests`.
2. `mkdocs build --strict` exits 0 in the builder image
   (`squidfunk/mkdocs-material:9.8.2`), and the warnings are read one by one.
3. `hack/check_docs_links.py` reports `0 broken relative links`.
4. `hack/check-charts.sh` still lints all charts after any chart README edit.
5. The board carries the stage's task card in `Validation` with the branch, the PR and the output of
   the commands above.
6. The operator reads the stage on the `develop` site after its merge: one page per section followed
   end to end.

## 11. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| A pinned path moves and a chart comment now points at nothing | An operator following a comment lands on a 404 | R4 plus the `references` check; the plan lists every cited path before moving anything |
| `status.md` retired with an inbound link left behind | A 404 from the page people open first | `links` and `references` fail the stage-1 PR; the plan greps for it before deleting |
| Generated pages drift because someone edits them | Two answers to one question | Banner, `--check` in the required checks, and the rules page naming it |
| The banner and nav checks only guard changed pages | An untouched page keeps an old label indefinitely | The whole-tree report is the list; the staleness report covers the pages that matter, and neither fails a build |
| The staleness report is noisy on a busy chart directory | Cards filed for pages that are still true | `Sources` names files or directories deliberately; the pass reads the page before filing and says so on the card |
| Eight tabs overflow into a menu | A section gets harder to find | Stage 4 measures the tab strip; if it overflows, History folds into Agent work as "Records" |
| A security section that repeats `network.md` | Two homes for the same fact, the exact defect R1 names | Security states guarantees and proofs; `network.md` keeps the request path; the plan checks every new paragraph for a restated fact |
| The rules page becomes ceremony nobody reads | Nothing is enforced in practice | Every rule is checkable or names an artifact; the check script is the read |
| Cards for docs pile up behind the feature work | The staleness rotates into an endless backlog | One card per page, `priority/low` unless the page is a safety one, and a stage-4 card cap per pass |

## 12. Left to the builder

- The prose of every new page. The questions are fixed above; the voice is the operator's own, which
  `how-it-works/` already carries.
- The exact render of the two generated tables — columns, sorting, how a route with no middleware is
  shown.
- How `gen_docs.py` parses: YAML loading or a small walker. Loading is correct; the builder confirms
  it handles IngressRoutes that carry a middleware list and the backup file's nested streams.
- The wording of the generated banner and the staleness report, as long as both are stable.
- Whether `running-it/README.md` or `runbooks/README.md` owns the procedure index after Runbooks
  dissolves.
- The order of the two new tabs in the nav.
- Where the "not recorded" rows of `backup/everything.md` and `security/critical-points.md` point
  until the operator fills them: a blank, a Bitwarden item name, or a card.
