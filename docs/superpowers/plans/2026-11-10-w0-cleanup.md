# W0 — Longhorn Cleanup Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Remove every Longhorn object from the cluster and the repository, and leave a written record of which applications now need a fresh configuration.

**Architecture:** No data is rescued. The eleven volumes that still exist are abandoned by decision, so this workstream only has to stop the workloads that hold them, clear the finalizers that no CSI driver can clear any more, and delete the leftovers. It is half a session, and it unblocks everything else.

**Tech Stack:** kubectl (admin kubeconfig), git.

**Spec:** `docs/superpowers/specs/2026-11-10-homelab-stabilisation-design.md` §9 W0

## Global Constraints

- **The data is lost by decision.** Do not attempt recovery, do not mount the old volumes read-only "just in case", and do not spend a session on forensic work. The operator is reconfiguring every affected application from scratch.
- The builder has no cluster write access. Every cluster-side command is run by the operator, who pastes back the verification output.
- Removing the finalizers will make the volumes unrecoverable. That is intended, and is why Task 1 records the disposition of every affected application first.
- Do not delete an Application, a chart or a namespace unless Task 1 lists it as deleted. Everything else is rebuilt, not removed.
- `cluster/infrastructure/**` is applied by hand, so deleting those files has no cluster effect. Say so in the commit message rather than implying otherwise.

## Review Focus

1. **An application is deleted rather than rebuilt.** Task 1 fixes the disposition in writing before anything is removed, and Task 2 may only act on applications whose disposition is not "delete".
2. **A finalizer is cleared on a claim that is still in use.** Task 2 re-checks the live set against the inventory and refuses to patch anything unmatched.
3. **A pod restarts during the work and takes a claim with it.** Harmless here — the data is already abandoned — but it must not be mistaken for a fault. The age in Task 1's record explains it.
4. **`longhorn-system` hangs on finalizers.** Task 3 has an explicit escalation step instead of a blind delete.
5. **A repository file is deleted that something still references.** Task 3 greps for references before committing.

### Task 2: Stop the workloads and clear the claims

**Interfaces:**
- Consumes: `docs/cleanup/longhorn-disposition.md`.
- Produces: zero `Terminating` claims and zero Longhorn PVs.

- [ ] **Step 1: Stop the ten pods**

Any of these will be rebuilt in a later workstream, so stopping them now is deliberate. Because some
Applications have `selfHeal`, a manual scale is reverted — so for those, the honest action is to
delete the pods and let their controllers recreate them into `CrashLoopBackOff`, or to disable
`selfHeal` on that Application first.

Run, for each pod in the inventory:

```bash
kubectl -n "$NS" delete pod "$POD" --wait=false
```
Expected: ten pods terminating. They will be recreated and will not start, because their claims are
`Terminating`. That is the expected end state until their workstream rebuilds them.

If `selfHeal` fights this and the pod keeps coming back and holding the claim, disable automation on
that one Application in git, merge, and retry.

- [ ] **Step 2: Clear the claim finalizers, one at a time, with a guard**

```bash
for ref in $(kubectl get pvc -A -o json | jq -r '.items[] | select(.metadata.deletionTimestamp != null) | "\(.metadata.namespace) \(.metadata.name)"'); do
  set -- $ref
  echo "-> $1/$2"
  kubectl -n "$1" patch pvc "$2" -p '{"metadata":{"finalizers":null}}' --type=merge
done
kubectl get pvc -A | grep -i longhorn
```
Expected: the final `grep` prints nothing.

Stop immediately if the loop prints a namespace/name pair that is not in the disposition file.

- [ ] **Step 3: Clear the PV finalizers**

```bash
kubectl get pv -o json | jq -r '.items[] | select(.spec.csi.driver == "driver.longhorn.io") | .metadata.name' | while read -r pv; do
  echo "-> $pv"
  kubectl patch pv "$pv" -p '{"metadata":{"finalizers":null}}' --type=merge
done
kubectl get pv | grep -c longhorn
```
Expected: `0`.

- [ ] **Step 4: Confirm the cluster has no Longhorn claim or volume left**

```bash
kubectl get pvc -A | grep -ci longhorn
kubectl get pv | grep -ci longhorn
```
Expected: `0` twice.

### Task 3: Delete Longhorn from the cluster and the repository

**Files:**
- Delete: `cluster/infrastructure/storageclass/lh-performance.yaml`
- Delete: `cluster/infrastructure/storageclass/lh-performance-no-backup.yaml`
- Delete: `kubectl/ingressRoute/longhorn.yaml`
- Modify: `AGENTS.md`

- [ ] **Step 1: Delete the namespace**

```bash
kubectl delete namespace longhorn-system --wait=false
kubectl get ns longhorn-system -o json 2>/dev/null | jq -r '.spec.finalizers // "gone"'
```
Expected: `gone`, or `Terminating` at first and `gone` on a later check.

If it stays `Terminating`, inspect before patching:
```bash
kubectl get namespace longhorn-system -o json | jq '.status.conditions'
```
Report the condition rather than clearing it blind — a stuck namespace here usually means a webhook
or an APIService still points into it.

- [ ] **Step 2: Check for references before deleting the files**

```bash
grep -rn -i longhorn --include='*.yaml' --include='*.yml' . | grep -v '^./.git/'
```
Expected: the three files Task 3 deletes, plus any references inside `cluster/argocd/**` (which are
CRLF — read them with `tr -d '\r'` if a match is unclear).

If a reference points at a file that is *not* on the delete list, stop and add it to this task.

- [ ] **Step 3: Delete the repository leftovers**

```bash
git rm cluster/infrastructure/storageclass/lh-performance.yaml \
       cluster/infrastructure/storageclass/lh-performance-no-backup.yaml \
       kubectl/ingressRoute/longhorn.yaml
```
Note in the commit body that `cluster/infrastructure/**` is applied by hand, so removing these files
does not change the running cluster — the StorageClasses were already gone with the driver.

- [ ] **Step 4: Clean `AGENTS.md`**

Remove Longhorn from: the storage description in §2, the storage rules in §4, the known-issues list
in §7 where it refers to the deleted StorageClasses, and the placement paragraph in §4 where it
mentions Longhorn. Keep one historical sentence saying Longhorn was abandoned after a disk failure —
history belongs in the record, an active instruction does not.

- [ ] **Step 5: Verify**

```bash
grep -rn -i longhorn --include='*.md' --include='*.yaml' --include='*.yml' . | grep -v '^./docs/' | grep -v '^./.git/'
```
Expected: only the one historical sentence in `AGENTS.md`, if that is the wording chosen.

- [ ] **Step 6: Commit**

```bash
git add -A
git commit -m "🔥 chore: remove Longhorn from the cluster manifests and the docs

The storage layer was abandoned after the disk failure and its replica data is
gone. The eleven surviving volumes are abandoned by decision — every affected
application is reconfigured from scratch in a later workstream — so this only
clears the stuck claims and deletes the leftovers."
```
