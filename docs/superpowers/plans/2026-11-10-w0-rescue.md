# W0 — Rescue Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Copy the eleven configuration volumes that still exist onto the NAS, prove the copies are good, then remove Longhorn from the cluster and the repository without losing anything else.

**Architecture:** Ten running pods hold eleven volumes that Longhorn no longer backs. Because the claims are already `Terminating`, a pod restart is permanent loss, so nothing is restarted and no manifest is touched during the copy. Data is streamed from each container through `kubectl exec` and `ssh` straight onto the NAS, then verified on the NAS. Only after every copy verifies are the finalizers removed and the Longhorn remnants deleted.

**Tech Stack:** kubectl (admin kubeconfig), `tar`, `ssh` to `nas`, `jq`, `sqlite3`, git.

**Spec:** `docs/superpowers/specs/2026-11-10-homelab-stabilisation-design.md` §9 W0

## Global Constraints

- **Nothing may restart during W0.** No `kubectl rollout`, no scale down or up, no config change, no ArgoCD sync, no node reboot. A restart of any pod in the table below is permanent data loss for that app.
- The builder has no cluster write access. Every cluster-side command is run by the operator, who pastes back the verification output.
- Do not enable `selfHeal` or `prune` on any Application until this plan is complete.
- The NAS rescue directory is `/mnt/storage/rescue/` on the mechanical array, not on the `local-path` SSD.
- Copy nothing that is not backed by a doomed claim. Several of these pods also mount NFS volumes that survive, and copying those wastes hours.

## Review Focus

The failure modes most likely to bite, and the step that pins each one:

1. **A pod restarts mid-copy and the volume is gone.** Any command that touches a Deployment, a ReplicaSet or an Application risks this. Task 1 step 3 records the pod ages so a restart is detectable, and Task 7 is the only task allowed to modify anything.
2. **A live SQLite file is copied torn and opens as corrupt.** Task 4 copies, runs `PRAGMA integrity_check`, and applies the digest-comparison rule before accepting the database.
3. **The wrong mount is copied.** Several pods mount both a doomed claim and a surviving NFS volume. Task 1 generates the claim-to-mount mapping from the live pods; every later copy step names a claim, never a bare path.
4. **A truncated tarball is accepted because the pipe failed silently.** A failed `kubectl exec` still leaves a file on the NAS. Every copy is verified with `tar -t` plus a byte comparison against `du` inside the container.
5. **A finalizer is removed from a volume that something is still using.** Task 7 lists before it patches, and refuses to patch any claim whose pod is not in the inventory.

### Task 1: Pre-flight inventory

**Files:**
- Create: `docs/rescue/inventory.md`

**Interfaces:**
- Produces: the namespace/pod/claim/mount table that every later task reads. Later tasks refer to claims by name, never by path.

- [ ] **Step 1: Confirm every pod is still Running and record its age**

Run:
```bash
kubectl get pods -A -o wide | grep -Ei 'filebrowser|calibre|firefly-app|linkstack-|n8n-|syncthing-7|thelounge-|pgadmin4|prometheus-server|postiz-redis-master'
```
Expected: ten lines, all `Running`, all `READY` complete. Record the `AGE` column for each — an age that resets later in the plan means a pod restarted and its volume is already lost.

- [ ] **Step 2: Generate the claim-to-mount mapping**

Run:
```bash
for t in "media-stack app.kubernetes.io/name=filebrowser" \
         "media-stack app.kubernetes.io/name=calibre" \
         "firefly app.kubernetes.io/name=firefly-app" \
         "linkstack app.kubernetes.io/name=linkstack" \
         "n8n app.kubernetes.io/name=n8n" \
         "syncthing app.kubernetes.io/name=syncthing" \
         "thelounge app.kubernetes.io/name=thelounge" \
         "databases app.kubernetes.io/name=pgadmin4" \
         "monitoring app=prometheus,component=server" \
         "postiz app.kubernetes.io/instance=postiz,app.kubernetes.io/component=master"; do
  set -- $t; ns=$1; sel=$2
  for pod in $(kubectl -n "$ns" get pods -l "$sel" -o name | cut -d/ -f2); do
    kubectl -n "$ns" get pod "$pod" -o json | jq -r --arg ns "$ns" --arg pod "$pod" '
      .spec.containers[] as $c | ($c.volumeMounts // [])[] as $m |
      .spec.volumes[] | select(.name == $m.name) |
      select(.persistentVolumeClaim != null) |
      [$ns, $pod, $c.name, $m.mountPath, .persistentVolumeClaim.claimName] | @tsv'
  done
done
```
Expected: one `tab`-separated line per container volume, `namespace  pod  container  mountPath  claimName`.

- [ ] **Step 3: Write the inventory file**

Create `docs/rescue/inventory.md` containing: the output of Step 2 as a table, and the pod ages from Step 1. Add a line per row marking it `doomed` or `survives`, using the eleven-volume table above as the authority.

Verification: every one of the eleven claims appears exactly once with a `doomed` mark, and every row with a claim outside the eleven is marked `survives`.

- [ ] **Step 4: Commit**

```bash
git add docs/rescue/inventory.md
git commit -m "📝 docs: record the volumes W0 has to rescue"
```

### Task 3: Rescue the six large volumes

**Interfaces:**
- Consumes: claim names and mount paths from `docs/rescue/inventory.md`.
- Produces: six tar archives in `/mnt/storage/rescue/`, named `<app>-vol.tar`.

- [ ] **Step 1: Copy each volume, one at a time**

Run this once per row, substituting `NS`, `POD`, `MOUNT` and `APP` from the inventory:

```bash
kubectl -n "$NS" exec "$POD" -- tar -cf - -C "$MOUNT" . \
  | ssh nas "cat > /mnt/storage/rescue/${APP}-vol.tar"
```

Order: `calibre`, `firefly`, `linkstack`, `n8n`, `pgadmin`, `thelounge` (largest last).

Do not run two at once. If a copy has produced no progress for several minutes, stop and report rather than waiting indefinitely.

- [ ] **Step 2: Verify each archive immediately**

For each app, run:
```bash
ssh nas "tar -tf /mnt/storage/rescue/${APP}-vol.tar > /dev/null && echo TAR_OK"
ssh nas "ls -l /mnt/storage/rescue/${APP}-vol.tar"
kubectl -n "$NS" exec "$POD" -- du -sb "$MOUNT"
```
Expected: `TAR_OK` with no error; the NAS file size within a few percent of the in-container byte count (tar adds headers, so slightly larger).

If `TAR_OK` is missing, or the sizes differ by more than a few percent, the pipe failed — re-run Step 1 for that app before moving on. Never delete a failed copy later and never assume it worked.

- [ ] **Step 3: Commit nothing yet**

The manifest is written in Task 6, after every volume has verified.

### Task 4: Rescue the two filebrowser volumes

**Interfaces:**
- Consumes: the `filebrowser-config` and `filebrowser-db-2` rows from the inventory.
- Produces: `filebrowser-config-vol.tar` and `filebrowser-db-vol.tar`, plus a verified SQLite database.

- [ ] **Step 1: Copy both mounts**

```bash
kubectl -n media-stack exec "$POD" -- tar -cf - -C /config .   | ssh nas 'cat > /mnt/storage/rescue/filebrowser-config-vol.tar'
kubectl -n media-stack exec "$POD" -- tar -cf - -C /database . | ssh nas 'cat > /mnt/storage/rescue/filebrowser-db-vol.tar'
```

- [ ] **Step 2: Verify both archives**

```bash
ssh nas "for f in filebrowser-config-vol.tar filebrowser-db-vol.tar; do tar -tf /mnt/storage/rescue/\$f >/dev/null && echo \"\$f TAR_OK\"; done"
```
Expected: two `TAR_OK` lines.

- [ ] **Step 3: Check the SQLite database**

```bash
ssh nas 'cd /mnt/storage/rescue && mkdir -p fb-db && tar -xf filebrowser-db-vol.tar -C fb-db && f=$(find fb-db -name "*.db" | head -1) && echo "db=$f" && sqlite3 "$f" "PRAGMA integrity_check;"'
```
Expected: `ok`.

If the result is anything other than `ok`, this is the torn-copy case. Re-copy the mount a second time to a `.2.tar` and compare digests:

```bash
ssh nas 'sha256sum /mnt/storage/rescue/filebrowser-db-vol.tar /mnt/storage/rescue/filebrowser-db-vol.2.tar'
```
- Identical digests: the database was quiescent across both windows, keep the copy.
- Different digests: the app was writing. Keep the newest copy anyway, mark it `unverified` in the manifest, and plan to rebuild filebrowser's users and settings during W7. The files it indexes are on NFS and are not affected.

**Do not stop or scale the pod to quiesce the database.** That destroys the volume this task exists to save.

- [ ] **Step 4: Record the outcome**

Note in `docs/rescue/inventory.md` whether the database is `verified` or `unverified`, and why.

### Task 7: Remove the finalizers

**Interfaces:**
- Consumes: the eleven claims and their PVs.
- Produces: zero `Terminating` claims and zero `longhorn` PVs in the cluster.

- [ ] **Step 1: List before touching anything**

```bash
kubectl get pvc -A -o json | jq -r '.items[] | select(.metadata.deletionTimestamp != null) | "\(.metadata.namespace)/\(.metadata.name)\t\(.spec.storageClassName)\t\(.spec.volumeName)"'
```
Expected: eleven lines, all with class `longhorn` or `longhorn-static`. The `qbittorrent-download-nfs` claim is `Pending` rather than `Terminating` and does not appear here — it belongs to W1, not W0.

Stop and report if any line names a claim that is not in `docs/rescue/manifest.md` and not the two explicitly declined.

- [ ] **Step 2: Remove the claim finalizers**

```bash
for ref in $(kubectl get pvc -A -o json | jq -r '.items[] | select(.metadata.deletionTimestamp != null) | "\(.metadata.namespace) \(.metadata.name)"'); do
  set -- $ref
  kubectl -n "$1" patch pvc "$2" -p '{"metadata":{"finalizers":null}}' --type=merge
done
kubectl get pvc -A | grep -Ei 'terminating|longhorn' || echo NONE_LEFT
```
Expected: `NONE_LEFT`.

- [ ] **Step 3: Remove the PV finalizers**

```bash
kubectl get pv -o json | jq -r '.items[] | select(.spec.csi.driver == "driver.longhorn.io") | .metadata.name' | while read -r pv; do
  kubectl patch pv "$pv" -p '{"metadata":{"finalizers":null}}' --type=merge
done
kubectl get pv | grep -c longhorn
```
Expected: `0`. Any other number means a PV still references the driver — list them and report before continuing.

- [ ] **Step 4: Confirm no running pod was disturbed**

```bash
kubectl get pods -A -o wide | grep -Ei 'filebrowser|calibre|firefly-app|linkstack-|n8n-|syncthing-7|thelounge-|pgadmin4|prometheus-server|postiz-redis-master'
```
Expected: the same ten pods, same ages as Task 1. If any age reset, stop: that app's volume is gone and the copy is now the only source.
