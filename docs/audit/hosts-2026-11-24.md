## Operating system and kernel

Five hosts run Ubuntu 22.04.5 LTS (jammy) and one, `rbp0`, runs 24.04.4 LTS (noble). The two edge Pis
are therefore split across releases, and `rbp1` is the one still on jammy.

The kernels do not track the release either. `streaming` runs 6.8.0-149-generic on jammy, an HWE
kernel; `rbp0` runs 6.8.0-1060-raspi on noble; the other four are on 5.15 — 5.15.0-187-generic on
`nas` and `nuc0`, 5.15.0-1105-raspi on `rbp2` and `rbp1`. Every host reports cgroup v2, which is what
containerd and K3s expect.

Booted state matches the kernel file: the cmdline on each host names the running image, and no host
has an upgrade pending a reboot in the sense the collector records — `last boot` is 2026-08-13 on
`nas` and `nuc0`, 2026-11-22 on `streaming`, 2026-07-28 on `rbp0` and 2026-07-29 on `rbp2` and `rbp1`.

## Packages and their drift

The installed counts range from 952 on `nuc0` to 2073 on `streaming`. `streaming` is the outlier for a
reason: **908 package names appear there and on no other machine**, out of the 2073 its dpkg
selection lists. They include the CUDA toolkits 12.4, 12.5, 12.6, 12.8, 13.0, 13.1 and 13.2, a
`gedit` desktop editor, `gcc-12` and `g++-12`, and the OpenJDK 8 and 11 **runtimes** (`openjdk-8-jre`,
`openjdk-11-jre` — runtimes, not a JDK). That is a build host's package set, not a media server's.

Old kernels are never pruned. The collector's installed-kernel listing on `nas` prints 189
`linux-image-*` lines, 94 of them `linux-image-unsigned-*`, and 11 `linux-modules-extra-*`; the dpkg
selections behind it hold 95 `linux-image*` and 91 `linux-modules-extra-*` packages. `rbp2` carries
53 `linux-modules-extra-*raspi` entries, 18 of them installed and the rest `deinstall ok
config-files`, alongside 61 generic kernel packages left in the same state.

Held packages are zero on all six. `unattended-upgrades` is active on all six. The upgradable counts
at collection time were 45 (`nas`), 40 (`nuc0`), 151 (`streaming`), 31 (`rbp2`), 97 (`rbp0`) and 31
(`rbp1`).

## Containers

The runtime is present on five of six and different on nearly every one: Docker 29.4.2 on `nas` and
`nuc0`, 29.1.3 on `streaming`, 28.3.2 on both Pis. `rbp2` has no Docker at all — `docker version`
answers "missing".

**No container runs on any of the four cluster nodes.** `nas` and `nuc0` have `docker.service`
enabled and no containers, images or compose projects; `nas` keeps 17 anonymous volumes behind, the
residue of something run and removed. `streaming` has one image, `nvcr.io/nvidia/cuda:11.6.2-base-ubuntu20.04`,
and nothing running.

## K3s on the node

All four cluster nodes run `k3s version v1.36.6+k3s1 (fa45d6a5)`, Go 1.26.10, with binaries stamped
2026-11-24 between 01:27 and 01:34.

The three servers — `nuc0`, `streaming`, `rbp2` — run `k3s.service` with `server` on the command line
and the same `config.yaml`:

```yaml
disable:
  - traefik
  - local-storage
```

`nas` is the agent: it runs `k3s-agent.service`, has no `/etc/rancher/k3s/config.yaml` at all, and its
only role hint is `/var/lib/rancher/k3s/agent`. So the two addons this repository has taken over
itself are disabled on the control plane and never configured on the worker.

No server declares an `etcd-snapshot*` key, so no schedule and no S3 upload are configured on any of
the three. The only snapshots on disk are the five the upgrade plan wrote before each restart —
`pre-132-…` through `pre-136-…` on `nuc0` and `streaming`, 35 MB to 78 MB each — and no file named
`etcd-snapshot-*` exists anywhere. `nas`, as an agent, has neither.

The credential files are root-only: `/etc/rancher/k3s/k3s.yaml` and
`/var/lib/rancher/k3s/server/token` are both `0600 root:root` on the three servers.

## Storage, NFS exports and the disk union

`nas` is the storage host, and its `/etc/fstab` is the shape of it: ext4 disks at `/mnt/hdd0` through
`/mnt/hdd5`, `/mnt/snap` and `/mnt/ssd0`, all mounted by UUID, plus the LVM volume `/mnt/ultrafaststorage`
on `/dev/vg1/lvol0`. The data disks are combined by mergerfs into `/mnt/storage` — the fstab line
carries `minfreespace=50G`, `category.create=mfs` and `func.getattr=newest`. The union is 51 TB with
13 TB used, and root is 304 G free of 457 G.

`snapraid` 12.1-1 is installed. The root crontab runs it at 08:00:

```
00 08 * * * python2 /opt/snapraid-runner/snapraid-runner.py -c /opt/snapraid-runner/snapraid-runner.conf
```

`python2` is not installed on the host — it is absent from the package selection — so that line cannot
execute as written.

## GPU

`streaming` is the only machine with a GPU. `nvidia-smi` reports a **Quadro P400**, 2 GiB, driver
**580.178.04** (NVRM built 2026-07-07, GCC 12.3.0). The NVIDIA Container Toolkit is 1.19.0.

The kernel module is DKMS-built, and `dkms status` prints five targets:
`nvidia-srv/580.178.04` for 5.15.0-204-generic, 5.15.0-91-generic, 6.5.0-28-generic, 6.8.0-138-generic
and 6.8.0-149-generic. The last is the kernel the host is running, so the live module is covered.

`nas` has no NVIDIA hardware: `nvidia-smi` prints nothing, and the three `nvidia-*` packages present
(`nvidia-common`, `nvidia-libopencl1-dev`, `nvidia-prime`) are the Ubuntu metapackage trio. What it
does carry is a hand-built Intel driver, `intel-i915-dkms 1.23.5.19.230406.21.5.17.0.1034+i38-1`,
registered for two 5.15 kernels. Its own entry is broken: `dkms status` prints
`Error! Could not locate dkms.conf file. File: /var/lib/dkms/intel-platform-cse-dkms/2022.28/source/dkms.conf does not exist.`

## The two edge Pis

`rbp0` and `rbp1` are Raspberry Pi 4 Model B boards, Rev 1.4 both, arm64. They are not on SD cards:
`rbp0`'s root is `root=LABEL=writable` on a USB-attached disk, `rbp1` the same, and the kernel cmdline
of both is the Pi firmware's line rather than an Ubuntu one. `/boot/firmware` is the `system-boot` FAT
partition on that disk, and `arm_64bit=1` is set in its config, which is why the kernel is `-raspi`
and not the 32-bit default.

They differ in release: `rbp0` is 24.04.4 noble with 6.8.0-1060-raspi, `rbp1` is 22.04.5 jammy with
5.15.0-1105-raspi.

Both run a root crontab at 04:00 pointing at `/home/vronteix/scripts/backup.sh`. That script was not
read.

## Network, firewall and time

`ufw` is installed on five of the six and its service is enabled on those five. `ufw status` is
**inactive** on all five, and `streaming` has no `ufw` at all — not installed, not enabled, its
`firewall: ufw` probe returns nothing. The only packet-filter rules present anywhere are the ones
Docker and Kubernetes install for themselves: `DOCKER`, `DOCKER-USER`, `DOCKER-ISOLATION-STAGE-1/2`,
and the K3s `KUBE-*` chains. No host has a rule set of its own.

What that leaves published is worth naming, because Docker's DNAT bypasses a host firewall anyway:
`rbp0` forwards `5000/tcp` (the wg-easy admin UI, over plain HTTP), `9902/tcp` (the smartctl
exporter) and `51821/udp` from every interface; `rbp1` forwards the same `5000` and `9902` plus
`51822/udp`.

On the cluster nodes the whole `/24` reaches `6443`, `10250`, `111` and `2049`, plus `9100` on every
node and each server's etcd on `2379`/`2380` bound to its own LAN address.

The time zone is `Etc/UTC` everywhere, the RTC is not in local time, `systemd-timesyncd` is the active
clock service and `chrony`, `ntp` and `ntpsec` are all inactive, and `timedatectl` reports the system
clock synchronised on every host.

## SSH and sudo

The four cluster nodes have `PermitRootLogin no` and `PasswordAuthentication no`. Both Pis have
`PasswordAuthentication yes`, so the DNS and VPN hosts still accept a password.

X11 forwarding is enabled on all six. Ubuntu Pro is not attached on any host: `pro status` reports
`"attached": false` with an empty account on every one, so no ESM service is in use.

`/etc/sudoers` itself was read this time. All six carry the stock Ubuntu lines plus one hand-added
grant, `%admins ALL=(ALL) NOPASSWD: ALL`, and the operator's account is in `admins` on every host —
`admins:x:1001:vronteix` on `nas`, `x:1004` on `rbp0`. There are no drop-ins beyond the packaged
`README`. In effect passwordless root is granted by a group membership, which `visudo` does not show
and which no file under `/etc/sudoers.d` records.

## Upgrade readiness

- Ubuntu Pro is un-attached everywhere, so ESM coverage is not in place on the jammy hosts.
- Held packages: zero on all six.
- The release check was run this time. The five jammy hosts are each offered **`24.04.5 LTS`** and
  `rbp0`, already noble, is offered **`26.04.1 LTS`** — so the move is one hop for the Pis' newer
  board and two for everything else, and no host is offered anything other than an LTS.
- Pending dist-upgrade counts: `streaming` 151, `rbp0` 100, `nuc0` 43, `nas` 42, `rbp1` 41, `rbp2` 31.
- Free space is not a constraint on root: the tightest is `streaming` at 76 G of 228 G. The Pis' FAT
  boot partition is the one to watch — `rbp2` has 64 M free of 253 M and `rbp0` 62 M, and a release
  upgrade writes a new kernel and firmware there.
- Reclaimable before the move: `streaming` holds **17 G in `/var/cache/apt/archives`**, `nas` 1.5 G of
  `/var/log` and 842 M in Docker's tree; the two Pis 0.6 G and 1.0 G in Docker's.
- `nas` cannot run its own snapraid cron: `python2` is missing. `snapraid status` run by hand works and
  reports 786,116 files across six data disks, 21.5 TB used, 0% fragmentation — so the parity data is
  intact and only the runner is broken.
- `nas` carries a broken DKMS registration (`intel-platform-cse-dkms`), which will fail a kernel
  upgrade in the same way each time.
- Kernel packages accumulate and are never removed; `nas` alone holds 95 `linux-image*` package
  entries and `rbp2` 53 `linux-modules-extra-*raspi` entries in mixed install states.
- Every node is on the same K3s patch, so an upgrade is a single version move rather than a mixed
  fleet.

## What this record does not cover

- **No firewall rule set exists to describe.** `ufw` is inactive on the five hosts that have it and
  absent on `streaming`, and the only chains are Docker's and Kubernetes's, so there is nothing to
  record beyond that absence and the published ports listed above.
- **The Pis' `/home/vronteix/scripts/backup.sh` was not read.** The crontab entry is known, the script
  is not.
- **`/opt/snapraid-runner` was not inspected.** Only that the path exists and the cron points into it.
  `snapraid status` was run by hand, so the parity itself is measured; the runner's configuration is
  not.
- **The mode of the Pis' three env files** (`pihole.env`, `wg-easy.env`, `.env`) is not in the record.
  The collector lists what exists under `/home/vronteix/dockers`, not what it is readable by.
- Disk sizes for the media trees are missing: the `du` sweep timed out after 25 seconds on `nas`.
