## Operating system and kernel

Five hosts run Ubuntu 22.04.5 LTS (jammy) and one, `rbp0`, runs 24.04.4 LTS (noble). The two edge Pis
are therefore split across releases, and `rbp1` is the one still on jammy.

The kernels do not track the release either. `streaming` runs 6.8.0-149-generic on jammy, an HWE
kernel; `rbp0` runs 6.8.0-1060-raspi on noble; the other four are on 5.15 — 5.15.0-187-generic on
`nas` and `nuc0`, 5.15.0-1105-raspi on `rbp2` and `rbp1`. Every host reports cgroup v2, which is what
containerd and K3s expect.

Booted state matches the kernel file: the cmdline on each host names the running image, and no host
has an upgrade pending a reboot in the sense the collector records — `last boot` is 2026-08-13 on
`nas` and `nuc0`, 2026-11-22 on `streaming`, 2026-07-28 on `rbp0` and 2026-07-29 on `rbp2` and `rbp1`.

## The two edge Pis

`rbp0` and `rbp1` are Raspberry Pi 4 Model B boards, Rev 1.4 both, arm64. They are not on SD cards:
`rbp0`'s root is `root=LABEL=writable` on a USB-attached disk, `rbp1` the same, and the kernel cmdline
of both is the Pi firmware's line rather than an Ubuntu one. `/boot/firmware` is the `system-boot` FAT
partition on that disk, and `arm_64bit=1` is set in its config, which is why the kernel is `-raspi`
and not the 32-bit default.

They differ in release: `rbp0` is 24.04.4 noble with 6.8.0-1060-raspi, `rbp1` is 22.04.5 jammy with
5.15.0-1105-raspi.

Both run a root crontab at 04:00 pointing at `/home/vronteix/scripts/backup.sh`. That script was not
read.

## Network, firewall and time

`ufw` is installed on five of the six and its service is enabled on those five. `ufw status` is
**inactive** on all five, and `streaming` has no `ufw` at all — not installed, not enabled, its
`firewall: ufw` probe returns nothing. The only packet-filter rules present anywhere are the ones
Docker and Kubernetes install for themselves: `DOCKER`, `DOCKER-USER`, `DOCKER-ISOLATION-STAGE-1/2`,
and the K3s `KUBE-*` chains. No host has a rule set of its own.

What that leaves published is worth naming, because Docker's DNAT bypasses a host firewall anyway:
`rbp0` forwards `5000/tcp` (the wg-easy admin UI, over plain HTTP), `9902/tcp` (the smartctl
exporter) and `51821/udp` from every interface; `rbp1` forwards the same `5000` and `9902` plus
`51822/udp`.

On the cluster nodes the whole `/24` reaches `6443`, `10250`, `111` and `2049`, plus `9100` on every
node and each server's etcd on `2379`/`2380` bound to its own LAN address.

The time zone is `Etc/UTC` everywhere, the RTC is not in local time, `systemd-timesyncd` is the active
clock service and `chrony`, `ntp` and `ntpsec` are all inactive, and `timedatectl` reports the system
clock synchronised on every host.

- Kernel packages accumulate and are never removed; `nas` alone holds 95 `linux-image*` package

## The boot partition on `rbp2`, freed (2026-11-25)

The move's gate asks for 120 MB free on `/boot/firmware`, because 26.04 writes a new kernel and firmware
there before anything else. It held 64 MB of 253 MB on 2026-11-24. The largest user after the boot set
itself was `flash-kernel`'s keep-one copy: it moves each file it replaces to `<name>.bak`, and the last
kernel install left 297 `.bak` files, 72.0 MB, including a 39.8 MB
`initrd.img.bak` and copies of all eight `start*.elf` blobs and the three `uboot_*.bin`. Every `.bak` has
a live counterpart: `vmlinuz.bak` and `start.elf.bak` are byte-identical to theirs, and the initrd copy is
an older 39.8 MB build of the 86.9 MB file that is live.

They were archived on the host (`rbp2`'s root filesystem holds 820 G) and then dropped from the partition:

```bash
sudo mkdir -p /var/backups/rbp2-boot-firmware
sudo sh -c 'cd /boot/firmware && find . -name "*.bak" -print0 | \
  tar -cf /var/backups/rbp2-boot-firmware/boot-firmware-bak-2026-11-25.tar --null -T -'
sudo sh -c 'cd /boot/firmware && find . -name "*.bak" -delete && sync'
df -h /boot/firmware
```

```text
before   /dev/sda1  253M  190M   64M  75%  /boot/firmware
after    /dev/sda1  253M  117M  136M  47%  /boot/firmware
```

What was not touched: `vmlinuz` (10514887 bytes) and `initrd.img` (86893652 bytes) still carry their
2026-11-24 07:41 timestamps, `uname -r` still reports `5.15.0-1105-raspi`, `k3s` is `active`, and the node
reports `Ready` on `v1.36.6+k3s1`. The archive holds all 297 entries and is the rollback if a boot file
is ever wanted back.

## The union and the parity, before `nas` moves

Measured on `nas` at 23:29 on 2026-11-24, on the release it runs today — 22.04.5, kernel
`5.15.0-187-generic`, `mergerfs` 2.33.3-1 — as the baseline the move's card asks for at each hop.

**The union answers.** `/mnt/storage` is `fuse.mergerfs` over `/mnt/hdd0` … `/mnt/hdd5` with the option
set `/etc/fstab` carries (`minfreespace=50G`, `category.create=mfs`, `func.getattr=newest`, `use_ino`,
`inodecalc=path-hash`, `cache.files=off`). A 4 MiB file from `/dev/urandom` written to `/mnt/storage`
landed on `/mnt/hdd5`, the branch with the most free space, which is what `mfs` asks for. Its sha256 —
`7ad0e499…a938b` — came back identical on a second read, through `cat`, and from `/mnt/hdd5` directly,
and removing it through the union removed it from the branch too.

**The parity does not.** `snapraid status` loads a content file of **2024-02-10** and warns that the array
is **not fully synced**, with a sync left in progress at 1 %; `snapraid.parity` and all six content files
carry that same date, and the oldest block was scrubbed 1,018 days ago, which is that day. The report is
therefore historical: it claims 5,351 GB used on `/mnt/hdd0` where `df` measures 1.1 TiB, because 5,351 GB
is what that disk held in February 2024. Two smaller lines from it: 245 files carry a zero sub-second
timestamp, and 2 % of the array has never been scrubbed.

**What that means for the move.** The 51 TB union is the one thing on these hosts no backup covers whole,
and it has had no parity matching its data for two years and nine months: a disk lost today loses what was
on it. The gate at `nas`'s hop is a *completed* sync, not a status command that merely exits. `roles/snapraid`
wrote its runner at 19:21 the same evening, so the first sync is 03:17 on 2026-11-25 — the 13 TiB the
union holds read, and up to 5 TiB of parity written, resumable across nights. Card #710 tracks it, and
card #705 waits on it.

**The disks are healthy.** `smartctl -H` reports `PASSED` on the six data disks and on the parity disk, and
the kernel log carries no I/O error for any of them.

## The parity, synced (2026-11-25)

Card #710, and with it the gate at `nas`'s hop. The forced sync ran as
`snapraid --force-empty sync` in the transient unit `snapraid-first-sync`, from 23:50:10 on 2026-11-24
to 08:59:27: 9 h 09 min, 14,014 GB read, and the parity file left at 4.49 TB with all six content
files saved at 09:00. It ended on `289 file errors` and exited 1 — the files the running stack rewrote
or removed under it, which is the churn the pass after it takes in.

The runner's own pass is the one the card asks for. `/usr/local/sbin/snapraid-sync` started at
08:59:52 without anyone at the keyboard, logged `sync finished` at 09:01:03 and `done` at 09:01:10,
exited 0, and wrote the marker the alert reads at 09:01:03. Seventy-one seconds, because all the first
pass left it was that churn.

`snapraid status` now prints `No sync is in progress.`, no `NOT fully synced` warning, and
`days ago of the last scrub/sync` at 0, with the oldest, median and newest block all at 0. It reads
45,717 files and 14,014 GB used. `snapraid diff` at 14:20 reports 45,396 files equal against 331
differences — 9 added, 1 removed, 321 updated — and every one of them is under `qbittorrent-config`:
the client rewriting fastresume, queue and log files as it runs, which is the churn the nightly sync
takes in.

Two things this pass leaves open. The array is `100% not scrubbed`, because no scrub has run since the
parity was rebuilt; the runner scrubs on the first Sunday of the month, so the first slice is
2026-12-06. And 03:17 is not when the day's run starts: cron had been up since 2026-11-19 when the host

## The union's tools, across the two releases (2026-11-25)

The union's line was rehearsed under the mergerfs each target release actually ships, before `nas`
takes either hop, because the tool is not the same one twice: mergerfs is **2.33.3-1** on jammy,
**2.33.5-1ubuntu2** in 24.04 and **2.40.2-5build1** in 26.04. A union whose option set the new package
rejects is a `/mnt/storage` that comes back empty with every disk still full, which is the failure this
check exists to find before the host is on the release that has it.

**The line mounts, and round-trips, under both.** In a throwaway `ubuntu:24.04` and `ubuntu:26.04`
container, mergerfs taken from each release's own archive, two tmpfs branches, and the option set
`ansible/roles/union/defaults/main.yml` writes
(`allow_other,noforget,use_ino,inodecalc=path-hash,cache.files=off,dropcacheonclose=true,minfreespace=100G,category.create=mfs,func.getattr=newest,moveonenospc=true,fsname=mergerfs`):
the line mounted through `mount` on an `/etc/fstab` entry — the path the boot takes, through
`/sbin/mount.mergerfs` on both — and a 2 MiB file written through the union read back with the same
sha256 through the union and from the branch it landed on, with its removal through the union removing
it from the branch. The `/mnt/hdd*` glob form was rehearsed on 26.04 too, since that glob is the first
field of the host's line. The line rehearsed is the host's line: `minfreespace=100G` from `roles/union`,
not the 50 GB of the hand-written entry it replaced.

**Two options the newer package has moved on from.** `allow_other` is deprecated from mergerfs 2.35,
which sets it itself, and `noforget` is no longer in 2.40's option list. 2.40.2 accepted both without a
message and exited 0, so the line stays as the role writes it rather than being rewritten for a release
the host has not reached.

**The 24.04 package ships its mount helper without setuid.** `/usr/bin/mergerfs-fusermount` is mode
`0755` in `2.33.5-1ubuntu2` where `/bin/fusermount` is `4755`, the packaging defect that makes a
mergerfs mount started by a normal user answer `Operation not permitted`. It does not reach this union:
the fstab mount is root's at boot. It would reach a union moved into a user unit or started by hand
from a login, which nobody should do here.

**`snapraid` is not from the archive at all.** `/usr/bin/snapraid` is a hand-installed binary dated
2022-01-30, 563,416 bytes, sha256 `85e8c945…f41ef`, dynamically linked, and it prints `vnone` where a
packaged build prints its release. `dpkg` holds no record of it, so neither hop replaces it and the
runner calls the same file on both sides of the move. Ubuntu would supply 12.3-1 in 24.04 and 13.0-1 in
26.04 if it were a package, which it is not. The 2022 binary loads and runs on both target releases'
glibc — 2.39 and 2.43 — printing its banner and stopping at the missing `/etc/snapraid.conf`, so the
upgrade does not strand the tool.

**What this leaves to the hop.** The containers ran the laptop's kernel, and mergerfs is a FUSE mount
whose behaviour follows the kernel it was built for, so the host's own kernels are still the thing the
hop checks: `findmnt -T /mnt/storage`, a file written and read back through the union, and `snapraid
status` on the real array, at 24.04 and again at 26.04.
